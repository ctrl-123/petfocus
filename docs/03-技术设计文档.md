## 1. 架构总览

### 1.1 设计原则（按优先级排序）

| # | 原则 | 含义 | 违反示例 |
|---|---|---|---|
| P1 | **本地优先（Local-First）** | 无网络时全部核心功能可用；**所有业务数据只在本机**；网络只用于「按设备 ID 结算金币/配额」与「AI 营养估算代理」两件事 | 把待办列表放在 `useEffect` 里 fetch 后才渲染；把业务数据存到云端 |
| P2 | **时钟不可信但必须自洽** | 所有计时用单调时钟推导，不依赖也不信任 `Date.now()` 递增 | 用 `setInterval` 每秒累加 1 秒 |
| P3 | **状态可重建** | 页面崩溃/刷新后能从持久化的「事实」重建界面状态 | 把「剩余秒数」当作唯一状态存起来 |
| P4 | **约束能力可降级** | 网页无原生能力时自动降级，UI 明确标注，绝不假装有拦截能力 | Web 端显示「已拦截 3 个应用」 |
| P5 | **业务规则可测试** | 计时、结算、配额、经济全部为纯函数，不依赖 DOM 与真实时间 | 在 React 组件里 `if (elapsed > 60)` 算金币 |
| P6 | **数值集中配置** | 所有可调数值来自 `config/`，组件内不得出现魔法数字 | 组件里写 `const PRICE = 150` |
| P7 | **安全默认关闭** | 记账/饮食数据默认不上云；原生进程默认不拦截热键 | 默认上传全部数据 |

### 2.2 架构决策记录（ADR）

#### ADR-001：为什么用 Web 应用而不是 Electron/Tauri

- **决策**：以 PWA Web 应用为主交付物，真实应用拦截由可选的原生伴侣进程补足。
- **背景**：用户需要「简历上可点开的链接」，同时需要「非白名单应用不能启动」。
- **理由**：链接可分享、面试官零安装即可体验，是简历场景的决定性因素；而拦截能力在浏览器中物理不可得，用最小原生进程补齐比整体上 Electron 更划算（Electron 会让「打开链接」变成「下载 100MB 安装包」）。
- **代价**：两套运行时、本地 WS 的兼容性限制（见 ADR-007）。
- **被否方案**：
  - Electron 主交付：安装门槛高，简历场景失败。
  - Tauri：本机无 Rust 工具链（已实测），引入新工具链成本高。
  - 纯 Web 不做原生：核心卖点残缺，PRD 的 `[原生]` 验收标准无法交付。

#### ADR-002：为什么用 IndexedDB（Dexie）而不是 localStorage

- **决策**：主数据存 IndexedDB，`localStorage` 只存轻量 UI 偏好与「乐观状态缓存」。
- **理由**：待办历史 + 会话记录 + 每日营养/记账在一年内可达数万条；IndexedDB 支持索引、游标、事务、结构化查询与版本迁移；localStorage 有 5MB 上限且同步阻塞主线程（会破坏 Live2D 的帧率）。
- **代价**：API 更复杂、需写迁移脚本；用 Dexie 承担复杂度。
- **被否方案**：纯 localStorage（容量与性能都不够）；SQLite WASM（体积与 OPFS 兼容性风险）。

#### ADR-003：为什么计时不用 setInterval 累加

- **决策**：会话只持久化「事实」（`startedAt`、`plannedMs`、`pausedIntervals[]`），剩余时间由「当前单调时钟 − startedAt − 暂停累计」推导；UI 用 `requestAnimationFrame` 或 1s 的 `setInterval` **仅做重绘触发**，不承担计数职责。
- **理由**：浏览器后台会节流 `setInterval`（后台标签可低至 1 次/分钟）；笔记本休眠/唤醒会让累加严重偏慢；页面刷新会丢失累加值。而 `performance.now()` 是单调时钟，不受系统时间被改动影响，且随休眠正确前进（`performance.timeOrigin + performance.now()` 可与墙钟对齐）。
- **代价**：需要处理「单调时钟与墙钟偏差」的异常检测（见 ADR-004 与第 12 章异常清单 E4）。
- **被否方案**：`setInterval` 累加（不可靠）；Web Worker 计时（仍被节流，且仍怕刷新）。

#### ADR-004：为什么配额与金币结算必须走服务端

- **决策**：配额消耗与金币入账以服务端函数 + `now()` 为权威；客户端只做乐观更新，服务端返回后校正。
- **理由**：用户改系统时间或清 `localStorage` 即可重置配额、刷金币，这会摧毁产品的核心契约（「强制」与「经济」）。服务端时间为准是最小可行的防作弊。
- **代价**：离线时无法立即得到权威结果 → 采用「乐观显示 + 入队补结算 + 异常标记」，且在结算页明确标注「待服务器确认」状态。
- **被否方案**：纯本地结算（可被随意篡改）；原生签名（复杂且仅覆盖桌面增强包用户）。

#### ADR-005：为什么用 Outbox 队列而不是「双写」

> ⚠️ **部分被 ADR-010 取代（2026-02-14）**：本 ADR 原用于「业务数据上云」。决策变更后，**业务数据不再上云**，因此原「LWW 冲突解决 / conflict_log」部分**已作废**。本条现仅适用于「结算与 AI 请求」这一类出网操作的重试队列（见 5.3）。

- **决策**：凡需要出网的操作（`SETTLE` / `CONSUME_QUOTA` / `CLAIM_GRANT` / `AI_NUTRITION`）先落本地库并同时写入 `outbox` 表（含操作类型、payload、UUID、重试次数）；后台按指数退避推送；成功后删除 outbox 记录。
- **理由**：本地优先要求写入永不失败；断网、跨天、崩溃后仍要保证「金币与配额一条都不丢」；幂等 UUID 让重试安全。
- **冲突解决**：~~LWW + conflict_log~~ **已作废**（无跨端写入，不存在业务数据冲突）。仅保留「结算幂等」：服务端以 UUID 去重，重复请求返回既有结果。
- **被否方案**：直接双写（断网即失败）；CRDT（本项目无跨端并发场景，CRDT 复杂度不划算）。

#### ADR-006：Live2D 技术方案与备选

- **决策**：首选 PixiJS 7 + `pixi-live2d-display` + **自托管**的 Cubism Web SDK（Core + Framework），模型与动作资源懒加载；若找不到同时满足「许可允许个人展示 + 有可切换部件/皮肤 + 体积 ≤ 8MB」的模型，则切换 Rive 或序列帧精灵图。
- **理由**：这是 Web 上渲染 Cubism 模型唯一成熟路径；自托管 Core 以避免 CSP 与第三方 CDN 的稳定性问题（Cubism Core 是从 CDN/本地加载的独立脚本，需在 `index.html` 中先于应用加载）。
- **必须验证的前置条件（编码第一天就要验）**：
  1. `live2dcubismcore.min.js` 能在本地加载且不违反 CSP；
  2. 选定模型的 `.model3.json` 中存在可切换的 `Parts` 或独立 `Textures`（决定换装方案是否成立）；
  3. 首屏（不含模型）性能达标，模型加载后帧率 ≥ 30 FPS（中端笔记本）。
- **换装实现路线（按优先级）**：
  1. 模型自带部件显隐（`model.setPartOpacity` / 替换 `Texture`）→ 最轻量；
  2. 同一模型的多套 `moc3` 皮肤 → 切换成本高但最灵活；
  3. 在模型上方用独立 Pixi 图层叠加「饰品精灵」（帽子/眼镜跟随头部参数变换）→ **最稳妥且与模型解耦，推荐作为默认方案**。
- **被否方案**：Unity WebGL（体积与加载时间不可接受）；Three.js + VRM（模型制作成本高，PRD 已排除 3D）；Lottie（纯二维矢量，无「跟随视线」的灵动感）。

#### ADR-007：网页与本地原生的通信方式

- **决策**：`WebSocket` 连接到 `ws://127.0.0.1:<port>`（端口在 41800–41899 间探测）。连接失败即视为「未安装增强包」，降级为 `[Web]` 模式。
- **已知限制（必须写进 README）**：
  - 页面为 HTTPS 时连接 `http/ws://127.0.0.1` 属于**混合内容**，现代 Chrome/Edge 允许回环例外，但可能触发 **Private Network Access** 预检；Firefox 与部分 Safari 版本会直接阻止。
  - 因此该能力**仅在桌面 Chrome/Edge 下承诺可用**，其他浏览器显示「增强包需要 Chrome/Edge」。
- **安全设计**：
  - 原生端**只监听 `127.0.0.1`**，绝不监听 `0.0.0.0`；
  - 首次连接需完成一次握手（原生端在托盘显示 6 位配对码，网页输入后建立长期 token）；
  - 原生端**只接受两类指令**：下发白名单、查询状态；**只发送两类数据**：违规进程名 + 时间戳、心跳。
  - 原生端不读取用户任何业务数据。
- **被否方案**：浏览器扩展（需上架或开发者模式，安装门槛与审核风险高）；Native Messaging（需要注册表安装清单，分发更重）；本地 HTTP 轮询（延迟高、易被页面阻塞）。

#### ADR-008：AI 能力的边界

- **决策**：AI 只用于两处——**饮食营养估算兜底** 与 **奖励话术的可选润色**；营养计算**优先走本地库**；所有 AI 调用经服务端 Edge Function 代理并缓存。
- **理由**：AI 输出的不确定性不适合做权威数值；本地库保证离线可用与零成本；服务端代理保护 API Key。
- **降级**：AI 不可用时，营养项标记为「待估算」并允许手动录入；话术改用本地文案库（每档 ≥ 8 条）。
- **缓存策略**：以「规范化食物名 + 份量」为键，命中缓存直接返回（命中率高，成本可忽略）。

#### ADR-009：不用 Redux / 不引入重型状态框架

- **决策**：Zustand 分片 + 领域层纯函数。
- **理由**：本项目状态虽多但耦合低（会话、宠物、待办、设置各自独立）；Redux 的样板代码对个人项目性价比低。

#### ADR-010：匿名设备 ID + 服务端结算，不做账号体系 ⭐

- **决策**（2026-02-14 需求方确认）：**不实现任何账号体系**——没有注册、登录、邮箱、密码、用户资料，界面上不出现「账号」概念。身份退化为一个**前端首次启动时自动生成的匿名 UUID（设备 ID）**，存于 `localStorage`，用户不可见、无感。该 ID 随每次结算请求发送到 **Supabase Edge Function**，用于区分记账端点并保证幂等。业务数据（待办、会话、统计、宠物、健身、饮食、记账）**全部只存本机 IndexedDB，不上云**。前端托管 **Vercel 免费版**，后端 **Supabase Edge Function 免费版**。
- **理由**：
  1. 用户明确否决了账号体系（省掉注册/登录/找回/资料/隐私合规等一整套复杂度），但**保留服务端结算**，以便仍能挡住「改系统时间刷金币」与「清缓存重置配额」这两类低成本作弊——这是「强制自律」类产品的底线。
  2. 数据只存本机进一步降低复杂度：**不需要云同步协议、不需要冲突解决、不需要备份策略**，也天然满足隐私最小化。
  3. 免费额度足够：结算请求是极低频小负载，AI 代理有缓存（详见 ADR-011）。
- **威胁模型与残余风险（必须如实标注，不得含糊）**：
  | 攻击方式 | 是否被挡住 | 机制 |
  |---|---|---|
  | 修改系统时间刷时长/刷币 | ✅ 挡住 | 服务端 `now()` 为权威 + 单调时钟计时（ADR-003） |
  | 修改 `localStorage` 里的设备 ID | ⚠️ 部分 | 有 HMAC 请求签名（密钥与 ID 同时生成、同存本地），**但密钥也在本地** |
  | 打开 DevTools 抄走设备 ID 与密钥后冒用 | ❌ **挡不住** | 纯前端无法隐藏秘密（浏览器无安全存储可用）；这是本架构的**已知残余风险** |
  | 伪造非法时长的会话记录 | 🟡 部分 | 服务端以「会话开始时间 → 当前服务端时间」为上限约束有效时长；异常值标记待复核并延迟入账 |
- **对本项目的定位说明**：本产品是**自律工具，不是对抗性安全系统**。威胁模型的目标是「让作弊比老实做事更麻烦」，而不是「不可能作弊」。README 与「关于」页必须用这个措辞如实说明，**禁止**出现「防作弊」「无法破解」一类承诺。
- **被否方案**：
  - **Supabase Auth（匿名/魔法链接）**：用户已明确否决；对「打开就该能用」的自律工具而言，任何登录流程都是多一步摩擦。
  - **纯本地结算（不要任何服务端账本）**：最简单且零后端存储，但改一下电脑时间就能无限重置每月 5 次配额，核心契约失效；且 AI 营养估算本来就需要服务端代理藏 Key，「完全无后端」并不成立。
  - **浏览器扩展 / 桌面端持有密钥**：安全性更好，但仅覆盖安装了扩展/增强包的用户，与 Web 主交付定位冲突。
- **后续可选强化（不在 MVP）**：把签名密钥存进 IndexedDB 的 `CryptoKey`（不可导出）以提升抄取门槛；或引入「恢复码」机制支持换机（需重新评估是否与「无账号」决策冲突，已在 PRD 16.1 标注为需重新决策项）。

#### ADR-011：零成本运行（免费额度约束与应对）

- **决策**：全栈运行在免费额度内，**月现金支出 0 元**（域名可选，非必需）。若未来产生实际成本，**优先降级功能而不是付费**。
- **依据（已查证的官方额度，2026-02-14）**：

| 服务 | 免费额度（关键项） | 本项目的实际消耗估算 | 余量 |
|---|---|---|---|
| Supabase Free | Edge Function **500,000 次调用/月**；数据库 **500 MB**；出口流量 **5 GB**；**2 个活跃项目** | 结算+AI 约 200–2,000 次/月（单人）；账本一年 < 10 MB | 约 250 倍以上余量 |
| Vercel Hobby | 个人非商业项目免费；静态托管 + 带宽额度 | 纯静态 PWA，几百 KB 级资源 | 充足 |
| 域名（可选） | — | 不买则用 `xxx.vercel.app` 免费子域 | — |
| Live2D Cubism SDK | **个人（一般用户）免 SDK 发布许可与费用**；免费模型素材可营利/非营利使用 | 0 | — |
| AI 营养估算 | 按量付费（唯一可能的变动成本） | **本地食物库优先**，只有冷门菜才调 AI；且有缓存。重度使用约 **1–3 元/月**；不配 Key 则为 0 | — |

- **必须处理的免费版陷阱：Supabase 免费项目「7 天不活动会被自动暂停」**（官方明确说明）。这会直接影响「简历链接长期可访问」这一核心目标。
  - **应对（按优先级）**：
    1. **前端完全可用性不依赖 Supabase**——业务数据本就在本机，结算不可用时降级为「待确认」队列（见 12.2 TR8）。因此**项目被暂停时，网页依然能正常打开和使用**，只是金币/配额暂不入账。这是本地优先架构带来的最大好处。
    2. 在 README 与「关于」页**如实说明**：简历读者看到的是完整可用的应用；若结算服务休眠，首次访问会自动唤醒或短暂延迟。
    3. 需要长期活跃时，用一个**极轻量的定时调用**（如每周一次的 GitHub Actions 定时任务或 Uptime 监控 ping）避免被判定为不活动——注意不要因此刷爆免费额度（每周 1 次 ≈ 4 次/月，可忽略）。
    4. 最坏情况的退路：把结算逻辑彻底改为本地（牺牲防篡改，见 ADR-010 被否方案「纯本地结算」），成本归零且无休眠问题。
- **成本护栏（编码阶段必须实现）**：
  - AI 调用**必须**有：本地库优先 → 服务端缓存 → 每设备每日调用上限（建议 20 次）→ 全局日预算上限（建议 200 次），超限直接返回 `AI_UNAVAILABLE` 并回退手动录入。
  - 结算接口做**客户端节流**（同一会话不重复提交；outbox 幂等），避免异常循环放大调用量。
  - 在设置页显示「本月结算与 AI 调用量」，让成本可见。
- **被否方案**：Pro 版（$25/月，约 180 元/月）——对个人作品无必要；自建 VPS（约 60–120 元/月）——复杂度与成本都更高，收益为零。

## 4. 数据模型

### 4.1 通用约定

| 约定 | 值 |
|---|---|
| 主键 | `id: string`（UUID v4），本地生成，跨端一致 |
| 时间戳 | 一律 `number`（Unix 毫秒，UTC）；**不存 ISO 字符串**，渲染时再格式化 |
| 时钟来源标记 | 重要记录带 `clockSource: 'monotonic' \| 'wall' \| 'server'` |
| 软删除 | `deletedAt?: number`；`null` 表示有效（同步删除需要墓碑记录） |
| 同步元数据 | 所有可同步实体带 `updatedAt`、`rev`（本地递增）、`dirty` |
| 枚举 | 一律 `SCREAMING_SNAKE` 字符串字面量联合类型，不用数字枚举 |

### 4.3 IndexedDB（Dexie）表与索引 ⭐ 业务数据的唯一归宿

> 依据 ADR-010：**下列所有表只存在于本机**，不上云、不镜像到服务端。`dirty` 字段的语义已变更——不再是「待同步到云端」，而是「**待服务端结算**」（仅对金币与配额有意义）。

| 表 | 主键 | 索引 | 说明 |
|---|---|---|---|
| `tasks` | `id` | `dayKey`, `startAt`, `status`, `[dayKey+status]` | 纯本地 |
| `sessions` | `id` | `kind`, `status`, `startedAt`, `[kind+startedAt]` | 纯本地；`settledAtServer` 表示服务端已确认结算 |
| `quotaLedger` | `id` | `scope`, `periodKey`, `[scope+periodKey]`, `confirmed` | 本地副本 + 与 `deviceId` 关联 |
| `coinLedger` | `id` | `dayKey`, `kind`, `serverTime`, `[dayKey+kind]`, `confirmed` | 本地副本 + 权威值以后端返回为准 |
| `pet` | `id` | — | 单例，纯本地 |
| `inventory` | `id` | `itemId` | 纯本地 |
| `fitnessCheckins` | `id` | `dayKey`, `[dayKey+itemName]` | 纯本地 |
| `fitnessRecords` | `id` | `dayKey` | 纯本地 |
| `mealEntries` | `id` | `dayKey`, `[dayKey+slot]`, `normalizedName` | 纯本地 |
| `financeEntries` | `id` | `dayKey`, `categoryId`, `[dayKey+type]`, `occurredAt` | 纯本地 |
| `financeCategories` / `financeBudgets` | `id` | `type` / `monthKey` | 纯本地 |
| `settings` | `id` | — | 单例 |
| `outbox` | `id` | `kind`, `status`, `nextRetryAt`, `[status+nextRetryAt]` | **仅结算与 AI 请求**的重试队列（不再承载业务数据上传） |
| `aiCache` | `key` | `key` | 营养估算本地缓存（服务端缓存命中则不算） |
| ~~`conflictLog`~~ | — | — | **已删除**：不再有跨端冲突（ADR-010） |

**已删除的表**：原设计中的 `conflictLog`（冲突历史）以及所有以云同步为目的的字段（`rev`、`lastSyncedAt`）。`rev` 保留仅用于本地并发写检测。

**迁移策略**：Dexie 版本号严格递增，每个 `version(n).stores({...}).upgrade(tx => ...)` 只做必要数据变换；所有迁移必须有测试（用假数据跑升级后断言）。

### 4.4 服务端表（Supabase Postgres，仅 3 张）⭐

> **重要变更（ADR-010）**：服务端**不再镜像本地业务数据**。待办、会话、统计、宠物、健身、饮食、记账等表**只存在于本机 IndexedDB**，服务端一张都不建。

服务端只保存「结算所需的抽象账本」与「AI 缓存」，共 3 张表：

```sql
-- ① 设备：匿名设备 ID 的登记与签名校验材料
create table public.devices (
  device_id      uuid primary key,                 -- 前端生成，非 auth.uid()

-- ② 金币账本：追加型（append-only），永不 UPDATE 金额
create table public.coin_ledger (
  id             uuid primary key,                 -- 客户端生成的 UUID，即幂等键
  device_id      uuid        not null references public.devices(device_id) on delete cascade,
  kind           text        not null,
  amount         integer     not null,
  balance_after  integer     not null,
  ref_id         text,
  breakdown      jsonb,
  day_key        text        not null,             -- 以服务端时间计算的 dayKey（04:00 边界）

-- ③ 配额账本：追加型，CONSUME/GRANT/REFUND 都只 INSERT

-- ④ AI 营养估算缓存（无设备关联，全局共享）
create table public.ai_nutrition_cache (
  cache_key      text primary key,                 -- normalize(foodName)|portion

  model          text,
```

**访问控制（不使用 `auth.uid()`、不使用按用户 RLS）**

| 项 | 做法 |
|---|---|
| 客户端能否直连这些表 | ❌ **不能**。启用 RLS 并**不创建任何 policy**（默认拒绝一切），同时撤销 `anon` / `authenticated` 的表权限。前端只用 `anon key` 调用 Edge Function，绝不直接读写表 |
| 谁写这些表 | 仅 Edge Function，使用 `service_role`（只存于函数环境变量，绝不出现在前端产物） |
| 每次请求如何识别设备 | 请求头带 `x-device-id` + `x-device-sig`（见 6.1 与 ADR-010）。函数先查 `devices` 校验签名，再以 `device_id` 作用域读写账本 |
| 防越权 | 任何请求都必须带合法签名；`device_id` 不存在则拒绝（除显式注册接口） |

**关键索引**

```sql
create index on public.coin_ledger  (device_id, day_key);
create index on public.coin_ledger  (device_id, server_time desc);
create index on public.quota_ledger (device_id, scope, period_key);
create unique index on public.coin_ledger  (id);   -- 幂等键
create unique index on public.quota_ledger (id);   -- 幂等键
```

**幂等与并发**：结算与扣配额都在**单个事务**内完成，入口先 `insert ... on conflict (id) do nothing`，若影响行数为 0 说明是重复请求，直接返回已有结果（不重复入账）。

**余额与剩余额度的求法**：因为账本是追加型，余额 = `sum(amount)`、剩余额度 = `count(GRANT) - count(CONSUME) + count(REFUND)`。数据量极大时可加物化快照表，MVP 不需要。

**服务端权威函数**

| 函数 | 职责 | 幂等键 |
|---|---|---|
| `register_device(p_device_id uuid, p_secret_hash text)` | 首次登记设备（前端生成 ID 与密钥，只上传密钥哈希） | `p_device_id` |
| `settle_session(p_device_id, p_session jsonb)` | 校验签名与合法性 → 用**服务端时间**约束有效时长上限 → 重算违规与质量系数 → 应用经济公式 → 写 `coin_ledger` → 返回权威余额 | `p_session.id` |
| `consume_quota(p_device_id, p_scope, p_period_key, p_session_id)` | 原子扣减配额（`select ... for update`），返回剩余额度；配额耗尽则返回越界代价 | `p_session_id + p_scope` |
| `claim_grant(p_device_id, p_scopes text[])` | 按**服务端时间**计算 periodKey 并补充每日/每月额度 | `scope + period_key` |
| `ai_nutrition(p_food, p_portion)` | 查缓存 → 命中即返回；未命中调模型 → 写缓存 → 返回 | `cache_key` |

**结算公式必须与前端 `domain/economy.ts` 逐字一致**，因此实现上：把经济公式写成**平台无关的纯函数**放在 `packages/shared`，Edge Function（Deno）与前端共同引用同一份源码，避免两套逻辑漂移。

### 5.1 会话引擎（Session Engine）

#### 5.1.1 状态机

```
                 ┌──────────────┐
   创建（到点/手动）│  SCHEDULED   │ 宽限期 3 分钟
                 └──────┬───────┘
        点「立即开始」/ 宽限期结束 │

                 │              │ ◀───────────────────

     时间到（用户在）│         │ 用户点结束
                    ▼         ▼
        ┌──────────────────┐  ┌──────────────┐
        │  SETTLED（自然）  │  │ 退出流程分支  │
        └──────────────────┘  └──────┬───────┘
                          ┌──────────┼──────────┬───────────┐
                          ▼          ▼          ▼           ▼
                    QUOTA_DAILY QUOTA_MONTHLY  SKIP      BREACH
                       (无损)      (无损)     (-10币)   (收益清零+罚款)
                                      │
                          时间到但用户不在 ▼
                                 ┌────────────────────┐
                                 │ AWAITING_SETTLEMENT │ 下次打开补结算
                                 └────────────────────┘
```

**不变量（Invariants，必须在测试中断言）**

| ID | 不变量 |
|---|---|
| INV-1 | 全局同时最多一个 `status ∈ {SCHEDULED, RUNNING, PAUSED, AWAITING_SETTLEMENT}` 的会话 |
| INV-2 | `effectiveMs ≤ plannedMs`（超出部分不计收益，但如实记录总时长） |
| INV-3 | `effectiveMs = sum(pausedIntervals 之外的时间段)` 在 `[startedAtMonotonic, endMonotonic]` 内 |
| INV-4 | 任何时刻 `coinBalance ≥ 0` |
| INV-5 | 一次会话最多产生一条 `FOCUS_DONE`/`LOCK_DONE` 的 `coinLedger` 记录（幂等） |
| INV-6 | 每个 `(scope, periodKey)` 的 `CONSUME` 条数 ≤ 该期 `GRANT` 条数 |
| INV-7 | `violations` 数组按 `startedAt` 升序，且最多一个元素 `endedAt === undefined` |

#### 5.1.2 有效时长算法（纯函数）

```ts
// domain/session-engine.ts
export interface TickInput {
  session: Pick<Session, 'startedAtMonotonic' | 'plannedMs' | 'pausedIntervals' | 'violations'>;
  nowMonotonic: number;
  nowWall: number;
  isVisible: boolean;
  violationThresholdMs: number; // 默认 30_000
}

export interface TickResult {
  effectiveMs: number;      // 已累计的有效时长
  pausedMs: number;         // 已累计的暂停时长
  remainingMs: number;      // 剩余
  isPaused: boolean;
  progress: number;         // 0–1，用于环形进度
  clockSkewMs: number;      // 墙钟与单调时钟的偏差
  shouldSettle: boolean;    // remainingMs <= 0
}

export function computeTick(input: TickInput): TickResult {
  const { session, nowMonotonic, nowWall } = input;

  // 1) 累计暂停时长（含尚未闭合的暂停区间，用 nowMonotonic 补齐）
  const pausedMs = session.pausedIntervals.reduce((sum, iv) => {
    const to = iv.to ?? nowMonotonic;
    return sum + Math.max(0, to - iv.from);
  }, 0);

  // 2) 已流逝总时长（单调时钟，不受系统时间影响、休眠后正确前进）
  const elapsedTotalMs = Math.max(0, nowMonotonic - session.startedAtMonotonic);

  // 3) 有效时长 = 总时长 − 暂停时长
  const effectiveMs = Math.max(0, Math.min(elapsedTotalMs - pausedMs, session.plannedMs));

  // 4) 时钟偏差：墙钟流逝 − 单调流逝（正常应接近 0）
  const wallElapsed = nowWall - (session.startedAtMonotonic /* 已在创建时对齐为墙钟近似值 */);
  const monotonicElapsed = elapsedTotalMs;
  const clockSkewMs = wallElapsed - monotonicElapsed;

  const remainingMs = Math.max(0, session.plannedMs - effectiveMs);

  return {
    effectiveMs,
    pausedMs,
    remainingMs,
    isPaused: session.pausedIntervals.some(iv => iv.to === undefined),
    progress: session.plannedMs === 0 ? 1 : effectiveMs / session.plannedMs,
    clockSkewMs,
    shouldSettle: remainingMs <= 0,
  };
}
```

> **实现要点**：`startedAtMonotonic` 存 `performance.timeOrigin + performance.now()`，其量纲与 `Date.now()` 接近，可直接相减做偏差检测。绝不用它渲染日历时间。

#### 5.1.3 违规检测算法

```ts
// 事件源 → 违规区间的开启/闭合
// 事件：visibilitychange(hidden) | window.blur | fullscreenchange(exit)
// 但"短暂切走"（< 阈值）不计为违规，只记录为一次"分心"

export function openViolation(
  session: Session, nowMonotonic: number, source: Violation['source'], detail?: string
): Session {
  if (session.pausedIntervals.some(iv => iv.to === undefined)) return session; // 已暂停，忽略重复事件
  const startedAt = session.startedAtMonotonic + (nowMonotonic - session.startedAtMonotonic);
  // 先开启一个"候选暂停"区间：未达阈值则不写入 violations，只在结算时丢弃
  return {
    ...session,
    status: 'RUNNING', // 状态不变，是否暂停由 computeTick 决定
    pausedIntervals: [...session.pausedIntervals, { from: nowMonotonic }],
    violations: [...session.violations, { startedAt: nowWallOf(nowMonotonic), durationMs: 0, source, detail }],
  };
}

export function closeViolation(session: Session, nowMonotonic: number, thresholdMs: number): Session {
  const idx = session.pausedIntervals.findLastIndex(iv => iv.to === undefined);
  if (idx < 0) return session;
  const intervals = session.pausedIntervals.slice();
  const opened = intervals[idx];
  const durationMs = nowMonotonic - opened.from;

  // 未达阈值：撤回暂停区间，并从 violations 中移除该条（视为"瞥了一眼"）
  if (durationMs < thresholdMs) {
    intervals.splice(idx, 1);
    const violations = session.violations.filter((_, i) => i !== session.violations.length - 1);
    return { ...session, pausedIntervals: intervals, violations };
  }

  intervals[idx] = { ...opened, to: nowMonotonic };
  const violations = session.violations.slice();
  violations[violations.length - 1] = { ...violations[violations.length - 1], durationMs };
  return {
    ...session,
    pausedIntervals: intervals,
    violations,
    status: 'PAUSED',
  };
}
```

**页面被关闭时存在未闭合的违规区间** → 恢复后用 `min(nowMonotonic, startedAtMonotonic + plannedMs)` 收口，并在结算时提示「检测到未正常结束的离开」，按保守口径（按整段算违规）计入。

#### 5.1.4 恢复与补偿（冷启动）

```ts
// 应用启动时的状态重建（在任何渲染之前执行）
export function reconstructSession(
  stored: Session | undefined,
  nowMonotonic: number,
  nowWall: number,
): { session?: Session; action: 'NONE' | 'RESUME_RUNNING' | 'PROMPT_ABANDONED' | 'AUTO_SETTLE' } {
  if (!stored) return { action: 'NONE' };
  if (stored.status === 'SETTLED' || stored.status === 'ABANDONED') return { action: 'NONE' };

  const tick = computeTick({ session: stored, nowMonotonic, nowWall, isVisible: true, violationThresholdMs: 30_000 });

  if (tick.shouldSettle) {
    // 已超时：自动进入待结算（不自动发币，等用户看到结算页确认）
    return { session: { ...stored, status: 'AWAITING_SETTLEMENT' }, action: 'AUTO_SETTLE' };
  }
  if (Math.abs(tick.clockSkewMs) > 60_000) {
    // 系统时间被改动过：继续计时但标记异常，结算时收益减半（PRD 第 17.3 节）
    return { session: { ...stored, clockSkewMs: tick.clockSkewMs, status: 'PAUSED' }, action: 'PROMPT_ABANDONED' };
  }
  return { session: { ...stored, status: 'RUNNING' }, action: 'RESUME_RUNNING' };
}
```

**落盘策略**：会话状态**不每秒写库**。只在以下时机持久化：创建、开始、暂停、恢复、违规开启/闭合、会话结束、以及每 **15 秒** 的兜底心跳（`dirty` 写入）。UI 的每秒刷新只读内存状态。

#### 5.1.5 自然日边界（04:00）

```ts
export function dayKeyOf(ts: number, boundaryHour = 4): string {
  const d = new Date(ts);
  if (d.getHours() < boundaryHour) d.setDate(d.getDate() - 1);
  return format(d, 'yyyy-MM-dd'); // date-fns
}

export function periodKeyOf(ts: number, scope: QuotaScope, boundaryHour = 4): string {
  return scope.endsWith('MONTHLY') ? format(new Date(ts), 'yyyy-MM') : dayKeyOf(ts, boundaryHour);
}
```

- 跨天会话归属**开始时刻**的 `dayKey`（PRD E15）。
- 每日配额在首次访问时通过 `claim_daily_grant` 补齐（服务端时间），前端在本地也生成 `GRANT` 记录以支持离线展示，联网后与服务端对齐。

### 5.3 本地优先与结算队列（无云同步）⭐

> 依据 ADR-010：**不存在业务数据同步**。本节只处理两件事：业务数据如何本地落盘，以及「金币/配额」如何可靠地送达服务端结算。
> 原「云同步 / 冲突解决 / 首登与退登」章节因决策变更**已整体移除**。

#### 5.3.1 写入路径

```
用户操作
  → usecase 校验（Zod）
  → 领域计算（纯函数）
  → 本地 IndexedDB 事务写入（实体表；若涉及金币/配额则同时写 outbox）
  → UI 立即更新（乐观）
  → 后台 SettlementWorker 取 outbox 推送
      ├ 成功 → 删除 outbox 记录；用服务端返回的权威余额/剩余额度**校正**本地值
      ├ 失败（网络） → 指数退避重试（1s、2s、4s … 上限 5 分钟）
      └ 标记异常（服务端 flagged）→ 保留记录并显示「待复核」，不阻塞用户
```

**关键点**：只有 `SETTLE`、`CONSUME_QUOTA`、`CLAIM_GRANT`、`AI_NUTRITION` 这四类操作进 outbox。**待办、宠物、饮食、记账等纯本地数据永不进队列**——它们没有远端目的地。

#### 5.3.3 设备身份与请求签名（ADR-010 的落地）

```ts
// 首次启动执行一次；放 localStorage（不进 IndexedDB，因为要在任何异步初始化之前可用）
export interface DeviceIdentity {
  deviceId: string;        // crypto.randomUUID()
  secret: string;          // crypto.getRandomValues → base64，仅存本机，从不上传
  createdAt: number;
  registered: boolean;     // 是否已在服务端 register_device 成功
}

// 每个结算请求的签名（防止"只改 localStorage 里的 ID"这类低成本作弊）
async function signRequest(secret: string, body: string, ts: number): Promise<string> {
  const key = await crypto.subtle.importKey(
    'raw', new TextEncoder().encode(secret), { name: 'HMAC', hash: 'SHA-256' }, false, ['sign'],
  );
  const mac = await crypto.subtle.sign('HMAC', key, new TextEncoder().encode(`${ts}.${body}`));
  return btoa(String.fromCharCode(...new Uint8Array(mac)));
}
```

**请求头**：`x-device-id`、`x-ts`（时间戳）、`x-device-sig`（签名）。
**服务端校验**：① `|now() - x-ts| ≤ 5 分钟` 防重放；② 用 `devices.secret_hash` 校验签名；③ 不通过则 401，且计入可疑次数，超阈值置 `SUSPECTED`。

> ⚠️ **必须如实告知的限制**：密钥也在前端，因此**签名只能挡「改 localStorage」这类低成本作弊，挡不住打开 DevTools 抄走密钥的人**。产品定位是自律工具而非对抗性安全系统。此措辞须原样出现在 README 与「关于」页，不得写「防作弊」或「无法破解」。

```ts
export interface FocusRewardInput {
  plannedMs: number;
  effectiveMs: number;
  violationMs: number;
  isPunctual: boolean;          // 计划时间 ±2 分钟内开始
  linkedToTask: boolean;
  exitKind: Session['exitKind'];
  dailyEarnedCoin: number;      // 当日已产出（用于日上限）
}

export function computeFocusReward(i: FocusRewardInput): {
  total: number;
  breakdown: { base: number; durationFactor: number; qualityFactor: number; punctual: number; penalty: number; capped: boolean };
} {
  if (i.exitKind === 'BREACH') {
    return { total: 0, breakdown: { base: 0, durationFactor: 0, qualityFactor: 0, punctual: 0, penalty: 0, capped: false } };
  }
  const durationFactor = durationFactorOf(i.plannedMs);
  const completion = i.plannedMs === 0 ? 1 : i.effectiveMs / i.plannedMs;
  const violationRatio = i.effectiveMs + i.violationMs === 0 ? 0 : i.violationMs / (i.effectiveMs + i.violationMs);

  let qualityFactor = qualityFactorOf(completion, violationRatio);
  if (violationRatio > 0.2) qualityFactor *= 0.5;

  let base = 20;
  if (!i.linkedToTask) base *= 0.8;

  const punctual = i.isPunctual ? 10 : 0;
  let total = Math.round(base * durationFactor * qualityFactor) + punctual;

  const remainingDailyCap = Math.max(0, DAILY_COIN_CAP - i.dailyEarnedCoin);
  const capped = total > remainingDailyCap;
  total = Math.min(total, remainingDailyCap);

  return { total, breakdown: { base, durationFactor, qualityFactor, punctual, penalty: 0, capped } };
}
```

**两侧一致性测试**：在 CI 中跑同一份 fixture 文件（如 `packages/shared/src/economy/__fixtures__/cases.json`），断言前端实现与 Edge Function 的返回值逐字节一致。

#### 5.4.2 幂等结算流程（设备 ID 版）

```
前端                                     服务端 Edge Function: settle_session
 会话结束
 ├─ 本地乐观计算 reward（用共享的纯函数）
 ├─ 写本地 coinLedger(confirmed = false)
 ├─ 写 outbox(SETTLE, id = session.id)
 ├─ 本地更新宠物状态（★ 宠物数据只在本机，
 │   服务端不参与宠物状态）
 └─ 显示结算页（标注「待服务器确认」）
                                          ① 校验 x-device-id / x-ts / x-device-sig
                                              └ 失败 → 401，计入可疑次数
                                          ② insert coin_ledger(id) ... on conflict do nothing
                                              ├ 影响行数 = 0 → 幂等命中，直接返回已有余额
                                              └ 影响行数 = 1 → 继续
                                          ③ 用服务端时间约束有效时长上限：
                                               effectiveMs ≤ min(上报值, now() - started_at)
                                               超出部分截断并计入违规
                                          ④ 调 computeFocusReward（与前端同一份源码）
                                          ⑤ 事务提交，返回权威余额与服务端时间
                                          ⑥ 检测到异常（偏差 > 阈值）→ flagged = true，
                                               收益仍入账但标记待复核，前端显示「复核中」
 收到响应
 ├─ 用权威余额校正本地 coinLedger 与 UI
 ├─ 标记 confirmed = true，删除 outbox 记录
 └─ 401/异常 → 保留记录并退避重试；连续失败在设置页提示
```

**注意**：宠物状态（心情/饱食度/精力）由**前端领域函数**计算并只写本地。这样服务端不需要知道宠物存在，也符合「业务数据不上云」。

#### 5.6.1 匹配算法

```
normalize(input):
  去空白 → 全角转半角 → 去语气词（"来一份/吃了/大概"）→ 数字与单位抽取
  → 生成 normalizedName（如 "西红柿炒蛋"）

lookup(normalizedName, portionValue, portionUnit):
  1) 精确命中别名表（aliases: Map<alias, foodId>）→ 返回 source: 'LOCAL_DB'
```

```
POST /api/ai/nutrition  { foodName, portion: { value, unit } }
  → Edge Function
      1) cacheKey = `${normalize(foodName)}|${portion.value}${portion.unit}`
```

### 5.7 统计聚合

```ts
export interface StatsRange { from: number; to: number; }

export interface DailyStat {
  dayKey: string;
  focusMs: number;
  lockMs: number;
  tasksPlanned: number;
  tasksDone: number;
```

| 指标 | 口径（必须唯一，避免各页面数字对不上） |
|---|---|
| 专注时长 | `sessions(kind=FOCUS, status=SETTLED)` 的 `effectiveMs` 之和 |
| 锁机时长 | 同上，`kind=LOCK`（用 `effectiveMs`，不用 `plannedMs`） |
| 完成任务数 | `tasks.status = DONE` 且 `completedAt ∈ range` |
| 完成率 | 完成数 / （完成 + MISSED + SKIPPED + DEFERRED 中已过期的） |
| 获得金币 | `coinLedger` 中 `amount > 0` 之和（不含 `DEMO`） |
| 违规总秒数 | 所有会话 `violations[].durationMs` 之和 |
| 环比 | `(本期 − 上期) / 上期`，上期为 0 时显示「—」而非 `Infinity` |

**专注日历分档**：`0` / `1–30` / `31–60` / `61–120` / `>120` 分钟，配色需通过对比度检查，且提供等价的文本列表（NFR-5.4）。

**性能**：聚合结果按 `(range, dataVersion)` 做内存缓存；`dataVersion` 在任意写入后自增。数据 > 5000 条时先按天 rollup 到 `daily_rollup` 表（可在 IndexedDB 中物化）。

## 6. 接口契约

### 6.1 内部：前端 ↔ 服务端（Supabase Edge Function）

**通用请求头**（除 `/api/time` 与设备注册外，全部必需）


**端点**

```http

  200:  { ok: true, coin: number, breakdown: object, balance: number,

  200:  { ok: true, remaining: { daily: number; monthly: number }, serverTime: number }
  409:  { ok: false, code: 'QUOTA_EXHAUSTED', cost: { coin: number, wiltingMinutes: number } }
  401:  { ok: false, code: 'BAD_SIGNATURE' }

POST /api/quota/claim
  body: { scopes: QuotaScope[] }
  200:  { ok: true, granted: Record<QuotaScope, number>, remaining: Record<QuotaScope, number>, serverTime: number }

POST /api/ai/nutrition
  body: { foodName: string, portion: { value: number, unit: 'SERVING'|'GRAM'|'ML' } }
  200:  { ok: true, nutrients: Nutrients, confidence: number, model: string, cached: boolean }
  503:  { ok: false, code: 'AI_UNAVAILABLE' }
```

1. **不接受任何业务数据**——请求体里出现待办、记账、饮食明细、宠物状态一律拒绝（422），这是「数据只在本机」的技术强制。

3. 所有响应包含 `serverTime`；错误统一 `{ ok: false, code, detail? }`。
4. 幂等键统一用客户端生成的 `sessionId` 或 outbox item 的 `id`。

**协议要求**：`protocol` 版本不匹配时双方都必须降级而非崩溃；断线后网页每 5 秒重连一次（最多持续整个会期），重连成功需重发 `SET_ALLOWLIST` + `SESSION_START`（状态幂等）。

## 8. 安全与隐私

| 面 | 措施 |
|---|---|
| API Key | 只存 Supabase Edge Function 的环境变量；前端产物中不得出现；CI 增加密钥扫描（`grep` 规则 + gitleaks） |
| 数据最小化 | **业务数据（待办/会话/统计/宠物/健身/饮食/记账）全部只在本机**，上云的仅有「设备 ID + 金币/配额账本」抽象计数与「食物名+份量」的 AI 请求 |
| 服务端访问控制 | **不使用 Supabase Auth、不使用按用户 RLS**。`devices` / `coin_ledger` / `quota_ledger` / `ai_nutrition_cache` 全部启用 RLS 且**不创建任何 policy**（默认全拒），并撤销 `anon` 与 `authenticated` 的表权限；只有 Edge Function 用 `service_role` 访问 |
| 设备请求鉴权 | `x-device-id` + `x-ts` + `x-device-sig`（HMAC-SHA256）。服务端校验时间窗（±5 分钟）防重放、校验签名、可疑次数超阈值置 `SUSPECTED` |
| **残余风险（必须如实公示）** | 密钥存在前端，**打开 DevTools 可抄走设备 ID 与密钥并冒用**。本产品是自律工具（让作弊比老实做事更麻烦），**不是对抗性安全系统**。此措辞须出现在 README 与「关于」页；**禁止**使用「防作弊」「无法破解」等承诺 |
| 本地数据 | IndexedDB 明文存储（浏览器隔离即边界）；导出文件为明文 JSON（含记账金额），导出时明确提示 |
| 数据可携带 | 支持一键导出/导入 JSON；清除数据前强制要求导出；无云端副本，故无「远程删除」需求 |
| 原生通道 | 仅回环、仅配对 token、指令白名单、协议版本校验、拒绝任何文件路径类指令 |
| 依赖安全 | 锁定版本（`pnpm-lock.yaml`）+ 定期 `pnpm audit`；不引入 > 3 个月无维护的依赖 |
| 第三方 | 无广告、无追踪脚本、无社交 SDK；Live2D 与营养库的来源与许可在「关于」页列明 |
| 内容安全 | 无用户生成内容（UGC）展示，无外部链接注入风险 |

## 9. 性能预算

| 指标 | 预算 | 手段 |
|---|---|---|

## 12. 已知技术风险与平台能力约束

### 12.1 平台能力约束（结构性，不是"风险"，是必须遵守的事实）

> 本节的每一条都不可通过"更努力地实现"绕过。任何试图绕过的实现都视为缺陷。
> 裁决依据见 `docs/research/01-需求研究报告.md` 第 5 节「可行性边界清单」。

| # | 约束 | 精确表述 | 架构上的应对 |
|---|---|---|---|
| C1 | 浏览器不能枚举/挂起/结束其他进程 | 任何 Web API（含扩展以外的所有页面能力）都无法读取进程列表或阻止 exe 启动 | 约束能力抽象为 `ProcessGuardAdapter`，Web 实现是 `noopProcessGuard`（只做可见性违规检测）；真实拦截只能由原生伴侣进程提供（ADR-007） |
| C2 | 浏览器不能阻止窗口关闭 | `beforeunload` 只能弹浏览器默认确认框，且仅在用户与页面交互过之后生效 | 状态必须可重建（ADR-003）、崩溃恢复（第 12.2 节 E2），不依赖"阻止关闭" |
| C3 | 后台标签页会被节流 | `setInterval` 在后台可低至 1 次/分钟，`requestAnimationFrame` 完全暂停 | 计时不依赖定时器精度（ADR-003）；渲染在不可见时主动停止（性能预算 9） |
| C4 | 页面关闭后 `setTimeout` 不再执行 | 无任何"页面内"机制能在浏览器关闭后触发动作 | 到点提醒有三条路径：页面存活定时器 / 打开时补偿提示 / v0.2 Web Push 或原生常驻（5.2.3） |
| C5 | 移动端 Web 无跨应用拦截能力 | iOS/Android 浏览器沙箱不允许，且无 MDM 时不可绕过 | 移动端保留待办/统计/宠物；拦截类 UI 显示「此能力需桌面端」（PRD NFR-4.2） |
| C6 | 计时与配额可被用户本地篡改 | 改系统时间或清存储即可重置本地状态 | 单调时钟 + 服务端时间权威 + 追加型账本 + 幂等键（ADR-004） |
| C7 | HTTPS 页面连 `ws://127.0.0.1` 并非全浏览器可用 | 混合内容与 Private Network Access 会导致部分浏览器（尤其 Firefox）直接阻止 | 仅承诺桌面 Chrome/Edge；提供连接诊断页；失败必须静默降级（TR1） |
| C8 | 强制全屏可被 `Esc` 退出 | 这是浏览器为防钓鱼强制保留的逃生通道，不可屏蔽 | 记录为越狱违规并有限重试（最多 3 次），不谎称无法退出（PRD AC-1.4.4） |
| C9 | 未签名的原生程序会被杀软/SmartScreen 警告 | 无代码签名证书时不可避免 | README 说明 + 提供 `--uninstall` + 永远允许用户退出（技术设计 5.2.4） |
| C10 | Live2D 模型受许可约束且体积可观 | Cubism SDK 商用需授权；单个模型常 3–10 MB | 模型懒加载、体积预算、署名；预案为 Rive/序列帧（ADR-006） |
| C11 | 服务端不可用时无法产生权威结算 | 网络故障或 BaaS 故障期间无法确认配额与金币 | 乐观本地 + 队列重试 + 明确「待确认」状态；提供离线宽容模式（TR8） |
| C12 | 多标签页会各自计时 | 每个标签有独立的 JS 运行时 | leader election（E19） |

**对外承诺的准确表述（README 与「关于」页必须一致）**

> 本应用在浏览器中**无法阻止你打开其他程序**——这是浏览器的安全规定，不是实现缺陷。
> 网页版提供的是「强制全屏 + 离开检测与记录 + 收益惩罚 + 到点唤回」的**软约束**。
> 需要真正的应用拦截时，请安装可选的 **Windows 原生增强包**；安装后由它结束/挂起非白名单进程，网页与之通过本机回环 WebSocket 通信。移动端不支持任何拦截能力。

### 12.2 技术风险登记

| ID | 风险 | 影响 | 缓解 | 触发时的替代方案 |
|---|---|---|---|---|
| TR1 | HTTPS 页面连 `ws://127.0.0.1` 被浏览器阻止 | 原生拦截不可用 | 仅承诺 Chrome/Edge；提供诊断页 | 改为原生端主动发起（原生做 WS 客户端，网页做服务端不可行）→ 最终退路是 Electron 版 |
| TR2 | Live2D Core 与打包器的 CSP/WASM 兼容问题 | 宠物不可用 | 自托管 + `index.html` 直引 + 第一天就做 spike | 切 Rive/序列帧 |
| TR3 | 找不到「许可 OK + 可换装 + 体积小」的模型 | 换装功能受限 | 叠加层饰品方案 + 模型内建部件优先 | 只做「整体皮肤切换」，减少部件级换装 |
| TR4 | IndexedDB 在隐私模式/存储压力下被清，或用户误清浏览器数据 | **永久丢失**（无云端副本） | 首次使用明确告知 + 一键导出 JSON + 距上次导出 > 14 天温和提醒 + 清除前强制导出 | 引导用户定期导出；提供导入恢复流程 |
| TR5 | 浏览器后台节流导致到点提醒不准 | 核心体验受损 | 单调时钟补偿 + 恢复时提示；原生模式由增强包负责 | v0.2 引入 Web Push |
| TR6 | 经济公式前后端漂移 | 结算纠纷（用户信任受损） | 共享同一份源码 + CI 契约测试 | — |
| TR7 | 多标签页同时计时导致重复入账 | 数据错乱 | leader election（E19）+ 幂等键 | — |
| TR8 | 服务端时间不可用（Supabase Edge Function 故障或免费额度耗尽） | 配额/金币无法确认 | 乐观本地 + 队列重试；明确显示「待确认」；AI 兜底自动关闭而本地食物库继续可用 | 提供**离线宽容模式**：服务端不可用期间照常使用，仅暂缓配额扣减与金币入账，恢复后补结算 |
